1. WHAT THIS PROJECT IS
================================================================================

Slotwise is a multi-tenant appointment booking SaaS:

  - Companies (organizations) configure locations, services, and staff (providers).
  - Customers book time slots on a public website (or embedded widget).
  - Staff manage the calendar in an admin dashboard.
  - Providers have their own smaller portal for their schedule and appointments.
  - The system sends email and WhatsApp confirmations, can charge for appointments
    via Stripe, syncs bookings to Google Calendar, and supports waitlists and reviews.

Think of it as: Calendly-style booking + admin back-office + optional payments,
built as a custom full-stack app (not a third-party widget only).

5. HOW THE SYSTEM WORKS (BIG PICTURE)
================================================================================

BOOKING (customer, no account required):
  1. Customer opens /book?org=demo-company&product=demo
  2. Frontend loads integration context (locations, services, branding colors)
  3. Wizard: pick service → provider (or "any") → date/time slot → enter details
     (name, email, phone required) → confirm
  4. If service has a price: redirect to Stripe Checkout (hosted page on Stripe)
  5. After payment: /book/complete creates the appointment via API
  6. If free service: appointment created immediately on confirm
  7. Email + WhatsApp notifications sent; Google Calendar event for provider if connected
  8. Customer gets manage link in email to cancel/reschedule/review

STAFF ADMIN:
  - Manages catalog, sees all appointments for the org (filtered by location),
    exports data, changes statuses, handles waitlist tab, configures settings/billing.

PROVIDER:
  - Sees only their appointments, edits own weekly schedule and blocked times,
    connects Google Calendar on dashboard.

DATA FLOW:
  Browser → fetch(API_URL, { credentials: 'include' }) → NestJS → Prisma → MySQL
  Mutations include CSRF header from GET /auth/csrf

8. BOOKING FLOW (CUSTOMER) — STEP BY STEP
================================================================================

STEP 0 — Load context
  - Reads URL: org (required slug), product (filters services), locationId,
    campaign, source, returnUrl, embed flag
  - Calls GET /integration/context → locations[], services[], branding

STEP 1 — Location (only if multiple locations)
  - User picks a location; services list reloads for that location

STEP 2 — Service
  - Lists services with duration and price (e.g. $49.00)
  - Selecting service resets provider/slot and payment state

STEP 3 — Provider
  - Lists providers linked to that service
  - "Any available" lets the system pick an free provider at booking time

STEP 4 — Date & time
  - Date input; fetches GET /availability/slots for that day
  - Shows available slots in location timezone; customer timezone shown for clarity
  - If no slots: option to join waitlist (email, name, preferred date)

STEP 5 — Details
  - Name, email (prefilled if logged in), phone (required)
  - Validates with Zod; explains email + WhatsApp notifications

STEP 6 — Confirm
  - Summary table: location, service, expert, times, contact, price
  - Free: "Confirm appointment" → POST /appointments/book
  - Paid: "Pay & book" → POST /payments/booking-checkout → redirect Stripe
    → return /book/complete → POST /appointments/book/checkout-complete

AFTER BOOKING
  - Confirmation screen with manage link (unless returnUrl redirect for embed partners)
  - Notifications enqueued (email + WhatsApp)
  - Provider Google Calendar updated if connected
  - Org webhook fired if configured

9. PAYMENTS (STRIPE)
================================================================================

TWO SEPARATE PAYMENT FLOWS — both use Stripe hosted Checkout (secret key only;
no publishable key on frontend).

A) CUSTOMER PAYS FOR AN APPOINTMENT
  - Trigger: service.priceCents > 0 (e.g. demo Product Demo = $49)
  - Flow: booking-checkout session → Stripe → book/checkout-complete
  - Stored on appointment: paymentStatus (paid/waived/not_required), stripePaymentIntentId,
    amountPaidCents
  - Currency: STRIPE_BOOKING_CURRENCY (default usd)
  - Dev: if STRIPE_SECRET_KEY missing, payment waived in non-production

B) ORGANIZATION PAYS FOR PRO PLAN
  - Trigger: Admin Settings → Subscribe with Stripe
  - Price: 1,000 AED / month (from billing.constants.ts; Stripe product prod_* in env)
  - Webhook checkout.session.completed activates Pro on organization
  - Free plan: 25 bookings/month; Pro: 10,000/month (enforced on book)

STRIPE WEBHOOK (required for Pro activation)
  URL: STRIPE_WEBHOOK_URL e.g. https://YOUR-NGROK.ngrok-free.dev/payments/webhook
  Secret: STRIPE_WEBHOOK_SECRET (whsec_...)
  Events: checkout.session.completed, subscription updated/deleted, invoice paid

ENV (payments):
  STRIPE_SECRET_KEY
  STRIPE_WEBHOOK_SECRET
  STRIPE_WEBHOOK_URL
  STRIPE_PRODUCT_PRO
  STRIPE_PRICE_PRO (optional; else first AED recurring price on product)
  STRIPE_BOOKING_CURRENCY

10. NOTIFICATIONS (EMAIL + WHATSAPP)
================================================================================

CHANNELS (dual — both run; failure of one does not block the other):
  1. Email — SMTP via nodemailer (Hostinger or any SMTP in .env)
  2. WhatsApp — Unipile API (UNIPILE_API_KEY, UNIPILE_API_URL, UNIPILE_API_WHATSAPP)

WHEN SENT:
  - Booking confirmation (customer + provider email if different)
  - Reminder 24 hours before
  - Reminder 1 hour before
  - Rescheduled
  - Cancelled
  - Waitlist notified when slot opens (email)

EMAIL:
  - If SMTP_HOST empty: logs to console (dev friendly)
  - HTML templates in apps/api/src/notifications/templates/

WHATSAPP:
  - Plain-text versions of appointment messages
  - Phone required on booking (E.164 recommended, e.g. +971501234567)
  - DEFAULT_PHONE_COUNTRY_CODE optional for numbers without country code

QUEUE:
  - Redis + BullMQ by default (REDIS_URL)
  - USE_SYNC_NOTIFICATIONS=true runs inline without Redis

SMS (Twilio):
  - Stub only — logs in dev; not production-ready

11. GOOGLE CALENDAR SYNC (PROVIDERS)
================================================================================

WHAT IT DOES:
  When a provider connects Google, new/updated/cancelled appointments create/update/delete

HOW TO CONNECT:
  Provider dashboard → "Connect Google Calendar" → Google OAuth → redirect back
  with ?calendar=connected

API:
  GET  /integrations/google/connect     (redirect to Google)
  GET  /integrations/google/callback    (public — saves tokens)
  GET  /integrations/google/status
  DELETE /integrations/google/disconnect

REQUIREMENTS:
  GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_REDIRECT_URI in .env
  Google Cloud: Calendar API enabled, OAuth consent screen, test users if in Testing mode

NOT IMPLEMENTED:
  Microsoft Outlook sync (stub endpoint only)

================================================================================
17. APPOINTMENTS LIFECYCLE & STATUSES
================================================================================

Statuses: pending, confirmed, checked_in, completed, cancelled, no_show

Typical flow:
  pending (if service requires approval) → confirmed → checked_in → completed
  cancelled / no_show from admin or customer (within cutoff)

Customer cancel/reschedule:
  - Limited by location.cancellationCutoffH before start
  - Max 3 reschedules per appointment (rescheduleCount)

manageToken: secret token in URL for /manage/[token] without login

Payment fields: paymentStatus, stripePaymentIntentId, amountPaidCents

googleCalendarEventId: links to provider's Google event

25. SECURITY
================================================================================

  - Passwords bcrypt-hashed
  - JWT access + refresh in httpOnly cookies
  - CSRF double-submit cookie on POST/PATCH/DELETE (except /health, /payments/webhook)

  - Google OAuth state signed with HMAC

29. HOW TO RUN LOCALLY
================================================================================

Prerequisites: Node 20+, MySQL 8, Redis/Memurai (or USE_SYNC_NOTIFICATIONS=true)

1. Copy .env.example to .env and fill DATABASE_URL, secrets
2. pnpm install (from repo root)
3. cd apps/api && npx prisma db push && npx prisma db seed
4. pnpm dev (or run api and web separately)
5. Open http://localhost:3000
6. API http://localhost:3001 — Swagger /api/docs

For Stripe webhooks locally: ngrok http 3001 → set STRIPE_WEBHOOK_URL
