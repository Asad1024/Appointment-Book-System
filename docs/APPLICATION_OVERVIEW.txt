1. EXECUTIVE SUMMARY
================================================================================

Slotwise is a production-grade, company-owned appointment scheduling platform.
It lets businesses offer public online booking, manage staff availability and
catalog (services/providers), run an admin operations center, and embed booking
into other products (CRM, marketing sites, partner apps like Leads Reach).

Primary goals:
  - Customers book appointments online without double-booking
  - Staff manage schedules, policies, and manual overrides
  - Engineering teams integrate booking via URLs, iframes, API keys, and webhooks
  - All appointment times stored in UTC; displayed in location/customer timezones
  - Audit trail for status changes and operational transparency

The system is a monorepo with:
  - NestJS REST API (apps/api) + Prisma ORM + MySQL
  - Next.js web app (apps/web) for public booking, admin, provider, and account UI
  - Shared packages for scheduling logic and TypeScript enums/types
  - Redis/Memurai + BullMQ for async notification jobs (optional sync mode for dev)

CORE ENTITIES

Organization
  - Multi-tenant root (single org in MVP; schema supports multiple orgs)
  - slug (unique), name, logo, primaryColor, bookingCurrency
  - allowedEmbedOrigins (JSON for iframe CSP-style control)
  - Legacy org-level webhookUrl/webhookSecret/webhookEnabled
  - Stripe subscription fields (plan, status, customer/subscription IDs)
  - Relations: locations, users, team invites, API keys, outbound webhooks,
    partner booking sessions

Location
  - Physical or logical site under an organization
  - timezone, address, phone
  - Policies: cancellationCutoffH (hours), leadTimeMinutes, bookingWindowDays
  - reminderOffsetsMinutes (JSON array of minutes-before-appointment)
  - Has providers, services, appointments

User
  - email (unique), passwordHash, name, role
  - Optional link to Provider record (provider staff login)
  - Email verification and password reset tokens
  - Roles: super_admin, org_admin, location_manager, provider, customer

Provider (staff resource who delivers services)
  - Belongs to a location; optional slug (unique per org)
  - bio, email, isActive, archivedAt (soft archive)
  - availabilityRules, blockedTimes, serviceProviders, appointments
  - Optional Google Calendar connection (ProviderCalendarConnection)

Service (bookable offering)
  - name, slug, description, durationMinutes
  - bufferBeforeMinutes, bufferAfterMinutes
  - priceCents (optional paid booking)
  - productKey (maps to ?product= integration filter)
  - requiresApproval, isActive, archivedAt
  - intakeFields (custom questions per service)

ServiceProvider (many-to-many)
  - Which providers can perform which services

AvailabilityRule
  - Weekly recurring windows: dayOfWeek (0-6), startTime, endTime (local strings)

BlockedTime
  - One-off unavailable ranges: startUtc, endUtc, optional reason

Customer
  - name, email, phone (email unique globally)
  - Optional link to User account
  - remindersEnabled, reminderOffsetsMinutes (per-customer overrides)

Appointment
  - organizationId, locationId, serviceId, providerId, customerId
  - startUtc, endUtc, timezone, customerTimezone
  - status (confirmed, pending, checked_in, completed, no_show, cancelled)
  - source (web, admin, api), product, campaign, returnUrl, metadata
  - manageToken (magic link secret, unique)
  - rescheduleCount, reminder tracking fields
  - paymentStatus, stripePaymentIntentId, amountPaidCents
  - googleCalendarEventId
  - intakeResponses, appointmentNotes, events (audit), notification logs, review

PartnerBookingSession
  - Short-lived token for secure partner links (no PII in URL)
  - Pre-filled customer/service/provider, ref, returnUrl, campaign, leadLabel
  - expiresAt, usedAt

ApiKey
  - Partner API keys: keyPrefix, keyHash (SHA-256), revoke support

OutboundWebhook
  - Multiple webhook endpoints per org (name, url, secret, isActive)

Waitlist
  - serviceId, optional providerId, preferredDate, customer contact
  - notifiedAt when slot becomes available

Review
  - Post-appointment rating (1-5) and comment via manage link

AppointmentNote
  - Staff-authored notes on appointments (CRUD with author tracking)

AppointmentEvent
  - Audit log entries: action, actor, payload JSON

NotificationLog
  - Per-message delivery tracking (email/whatsapp types)

IdempotencyRecord
  - Prevents duplicate bookings on retry (idempotencyKey on appointments)

  - Public routes: booking, availability slots, manage token pages, integration
    context, partner session resolution

  - Providers scoped to their own appointments on provider dashboard

7. HOW THE SYSTEM WORKS (CORE FLOWS)
================================================================================

7.1 PUBLIC BOOKING WIZARD FLOW
--------------------------------
1. User lands on /book?org=...&product=... (optional query params).
2. Frontend calls GET /integration/context?org=&product= to load branding,
   locations, filtered services, reminder presets.
3. User selects service → system loads providers for that service at location.
4. User selects provider or "any available provider".
5. Frontend calls GET /availability/slots with serviceId, providerId, date range.
   Backend uses packages/scheduling-core to:
     - Load provider weekly rules and blocked times
     - Load existing appointments
     - Apply service duration + buffers
     - Apply location leadTimeMinutes and bookingWindowDays
     - Return available slot start/end in UTC
6. User picks slot, enters details (and intake fields if configured).
7. If service has price: optional Stripe checkout flow before confirm.
8. POST /appointments/book with slot, customer info, source/product/campaign/ref.
9. Backend transaction:
     - Validates slot still available (overlap check with row lock)
     - Upserts customer by email
     - Creates appointment with manageToken
     - Records appointment event
     - Enqueues confirmation notifications
     - Fires outbound webhooks (appointment.booked)
     - Syncs Google Calendar if connected
10. UI shows confirmation; email sent with manage link; optional returnUrl redirect.

7.2 FILLED / EVENT BOOKING FLOW
--------------------------------
When serviceId and providerId are known (admin-generated link, partner session,
or /book/event URL):
  - Skips service/provider picker steps
  - Shows split calendar + time slot UI (Cal-style day picker)
  - Uses booking-day-picker CSS with org accent color (--booking-accent)
  - Partner session /b/[token] may pre-fill customer fields from server-side session

7.3 MANAGE APPOINTMENT FLOW
---------------------------
1. Customer opens /manage/[manageToken] from email.
2. GET /appointments/manage/:token returns appointment (public, token-gated).
3. Cancel: POST manage/:token/cancel — checks cancellationCutoffH from location.
4. Reschedule: POST manage/:token/reschedule with new slot — validates availability,
   increments rescheduleCount, sends emails + webhooks.
5. Review: POST /reviews/manage/:token after eligible status.

7.4 ADMIN MANUAL BOOKING
------------------------
From dashboard dialog: POST /appointments/admin/book
  - source: admin
  - Same overlap validation
  - Appears on calendar immediately; may trigger provider notification

7.5 PARTNER SECURE SESSION FLOW
---------------------------------
1. Partner server POST /partner/v1/booking-sessions with API key.
2. Payload includes ref, returnUrl, optional customer prefill, service/provider IDs.
3. API returns short URL https://book.example/b/{token} (15-minute expiry).
4. Customer browser has no PII in query string.
5. GET /partner/sessions/:token resolves session → redirects into booking UI.
6. On book, appointment carries ref for CRM webhook correlation.

7.6 TEAM INVITE FLOW
--------------------
1. Org admin POST /team/invites with email + role (+ optional providerId).
2. Invite email with link /invite/[token].
3. Recipient accepts: POST /team/invites/token/:token/accept — creates/updates user.

8. SCHEDULING ENGINE & AVAILABILITY RULES
================================================================================

Package: packages/scheduling-core (Luxon-based)

INPUTS
  - Provider weekly availability rules (day + local time strings)
  - Blocked time ranges (UTC)
  - Existing appointments (UTC ranges)
  - Service durationMinutes, bufferBeforeMinutes, bufferAfterMinutes
  - Location leadTimeMinutes (minimum notice before booking)
  - Location bookingWindowDays (how far ahead customers can book)
  - Location timezone for interpreting rules

OUTPUTS
  - Discrete bookable slots (startUtc, endUtc)

SPECIAL CASES
  - providerId = "any" → backend picks an available provider for chosen slot
  - Concurrency: appointments.service uses transaction + assertNoOverlap
  - Calendar bounds API for UI month navigation limits

LOCATION POLICIES (configurable per location)
  - cancellationCutoffH: hours before start when cancel no longer allowed
  - leadTimeMinutes: default 120 (2 hours minimum lead time)
  - bookingWindowDays: default 60 days ahead
  - reminderOffsetsMinutes: default [1440, 120, 60, 30] minutes before appointment

18. SECURITY, RATE LIMITING & RELIABILITY
================================================================================

  - JWT in httpOnly cookies (not localStorage for staff)
  - CSRF double-submit cookie pattern (GET /auth/csrf)
  - Global throttling: 10/sec burst, 100/min sustained
  - Partner API keys hashed at rest (SHA-256); only prefix stored for display
  - manageToken is unguessable UUID for customer self-service
  - Partner sessions expire (15 minutes default)
  - Booking idempotency keys prevent duplicate charges/bookings
  - GlobalHttpExceptionFilter for consistent API errors
  - Health checks for load balancers
  - Concurrency tests in apps/api (appointments.concurrency.spec.ts)
  - RBAC on all admin mutations
  - Public decorator marks booking/health/integration routes
