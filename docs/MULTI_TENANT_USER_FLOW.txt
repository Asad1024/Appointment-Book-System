1. SIMPLE EXPLANATION (READ THIS FIRST)
================================================================================

Slotwise is one SaaS product with many businesses (tenants) on it.

Think of it in three layers:

  LAYER A — PLATFORM (Slotwise the company)
    One internal “platform” organization and one role: super_admin.
    They use /platform/* to see ALL customer businesses, billing, and reports.
    They do NOT book appointments as a public clinic.

  LAYER B — TENANT BUSINESS (each company on Slotwise)
    Each company is an Organization row (slug like demo-company).
    Their staff use /admin/* (org_admin, location_manager) or /provider/* (provider).
    They get a booking link: /book?org=their-slug

  LAYER C — END CUSTOMER (person booking an appointment)
    Usually a guest (no account). Optionally registers with ?org= on the URL.
    They use /book, /manage/[token], and /account — always tied to ONE tenant
    when they have an account.

The most important rule for customers:

  WITHOUT ?org=  →  generic /book shows “Booking link required” (OrgRequiredGate).
  WITH ?org=demo-company  →  booking runs in Demo Company’s catalog and timezone.

The most important rule for new businesses:

  WITHOUT ?org=  →  /signup creates a NEW organization + org_admin user.
  They never pick a company from a list; they ARE the new company.

Super admin is not “admin of one company.” Super admin is “operator of the whole
platform” with a separate UI that looks like admin but scopes data to all tenants.

2. THE THREE KINDS OF PEOPLE ON THE PRODUCT
================================================================================

We use the word “admin” in conversation for two different roles. In code they are
separate:

  ┌─────────────────────┬──────────────────┬────────────────────────────────────┐
  │ Everyday name       │ Role in database │ Primary UI                         │
  ├─────────────────────┼──────────────────┼────────────────────────────────────┤
  │ Super admin         │ super_admin      │ /platform/dashboard, /platform/…   │
  │ Org admin (tenant)  │ org_admin        │ /admin/dashboard, /admin/…         │
  │ Manager             │ location_manager │ /admin/… (subset of nav)           │
  │ Provider (staff)    │ provider         │ /provider/dashboard                │
  │ Customer            │ customer         │ /account (after register + verify) │
  │ Guest booker        │ (no user row)    │ /book?org=…, /manage/[token]       │
  └─────────────────────┴──────────────────┴────────────────────────────────────┘

Also defined in code:
  packages/shared-types/src/index.ts  →  UserRole enum, STAFF_ROLES, PLATFORM_ORG_SLUG

Staff roles (can use staff cookies + CSRF):
  super_admin, org_admin, location_manager, provider

Customers are NOT staff. They use the same login page but land on /account.

3. ORGANIZATIONS: WHO OWNS WHAT DATA
================================================================================

Every User belongs to exactly one Organization (organizationId on User).

Almost all business data is scoped by organization:
  - Locations, services, providers, appointments, API keys, webhooks, team members

TENANT organizations
  - Created by business signup (/signup → POST /platform/signup)
  - Or seeded for dev (e.g. slug demo-company = “Demo Company”)
  - slug is used in public URLs: ?org=demo-company
  - isActive flag: when false, public booking and customer register are blocked

PLATFORM organization (internal only)
  - slug: slotwise-platform  (constant PLATFORM_ORG_SLUG in shared-types)
  - Holds the super_admin user(s) in the database
  - Hidden from tenant lists and public booking (treated as “not found”)
  - Never used as a customer-facing booking target

Why a platform org exists at all:
  - Users table requires organizationId
  - Super admin is still a User row, but their org is not a “customer business”

Seed creates both:
  apps/api/prisma/seed.ts
    - Platform org + superadmin@slotwise.local
    - Demo tenant demo-company + org admin / providers / services

4. TWO DIFFERENT “FRONT DOORS” (URLS)
================================================================================

┌──────────────────────────────────────────────────────────────────────────────┐
│ FLOW 1 — NO ORG IN URL (platform / business marketing)                       │
├──────────────────────────────────────────────────────────────────────────────┤
│ /signup          → New business registers (creates tenant + org_admin)      │
│ /login           → Staff or customer; redirect depends on role                │
│ /book (no org)   → OrgRequiredGate — explains they need provider’s link       │
│ /register (no org) → OrgRequiredGate — customer must use ?org=                │
└──────────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────────────┐
│ FLOW 2 — ORG IN URL (tenant-scoped customer experience)                      │
├──────────────────────────────────────────────────────────────────────────────┤
│ /book?org=demo-company              → Booking wizard for that tenant           │
│ /book/event?org=…&serviceId&providerId  → Single-page event booking          │
│ /book/[providerSlug]/[serviceSlug]?org=…  → Pretty URLs (org still required) │
│ /register?org=demo-company          → Customer account for THAT tenant only   │
│ /login?org=demo-company             → Login then /account (scoped appts)     │
│ Partner/embed URLs                  → Partner API keys are per-organization    │
└──────────────────────────────────────────────────────────────────────────────┘

OrgRequiredGate (web):
  apps/web/src/components/booking/OrgRequiredGate.tsx
  Used by: BookingWizard, FilledBooking, book/event, register page, etc.

Booking link helper (API + admin UI):
  apps/api/src/common/booking-link.util.ts
  Builds URLs with ?org= and optional tracking params.

5. END-TO-END JOURNEYS (WHO DOES WHAT)
================================================================================

--------------------------------------------------------------------------------
5A. NEW BUSINESS SIGNS UP (BECOMES TENANT ADMIN)
--------------------------------------------------------------------------------

  User visits     /signup
  Fills form      company name, admin name, email, password, timezone
  API             POST /platform/signup  (public, rate-limited)
  Backend         PlatformService.signupBusiness()
                    - Rejects slug equal to slotwise-platform
                    - Creates Organization (isActive: true)
                    - Creates default Location “Main Office”
                    - Creates User with role org_admin
                    - Sets auth cookies (logged in immediately)
  Web redirect    /admin/dashboard

  Customer booking URL returned in API response:
    {WEB_URL}/book?org={new-slug}

  Files:
    apps/web/src/app/signup/page.tsx
    apps/api/src/platform/platform.controller.ts
    apps/api/src/platform/platform.service.ts

--------------------------------------------------------------------------------
5B. SUPER ADMIN OPERATES THE PLATFORM
--------------------------------------------------------------------------------

  User            Created in seed (or manually) with role super_admin
                  organizationId = platform org (slotwise-platform)

  Login           /login  →  redirect /platform/dashboard
  Session guard   usePlatformSession() — only accepts role super_admin
  Layout          apps/web/src/app/platform/layout.tsx
                    AdminLayout with shell="platform"
  Nav             platform-shell-config.ts
                    Dashboard, Organizations, Payments, Reports
  Scope switcher  PlatformScopeSwitcher (UI mirror of LocationSwitcher;
                  “All organizations” — future filter hook)

  API             All routes under /platform/* except POST /platform/signup
                  Protected by: JwtAuthGuard + PlatformAdminGuard
                  Lists exclude PLATFORM_ORG_SLUG via tenantWhere()

  Important:    Super admin visiting /admin/* is redirected to /platform/*
                  (apps/web/src/app/admin/layout.tsx)

  Files:
    apps/api/src/platform/platform-admin.guard.ts
    apps/web/src/lib/usePlatformSession.ts
    apps/web/src/lib/auth-redirect.ts

--------------------------------------------------------------------------------
5C. TENANT ADMIN / MANAGER RUNS THE BUSINESS
--------------------------------------------------------------------------------

  User            org_admin or location_manager on a TENANT org
  Login           /login  →  /admin/dashboard
  Session         useStaffSession() — rejects super_admin and customer
  Layout          apps/web/src/app/admin/layout.tsx
                    AdminLayout shell="tenant" + AdminLocationProvider
  Scope           LocationSwitcher picks active location within their org
  Data            All admin API calls use JWT orgId / location context

  Invited via     Team page (org_admin invites org_admin | location_manager | provider)

  Files:
    apps/web/src/lib/tenant-shell-config.ts
    apps/web/src/lib/useStaffSession.ts

--------------------------------------------------------------------------------
5D. PROVIDER (STAFF WITH OWN CALENDAR)
--------------------------------------------------------------------------------

  Login           /login  →  /provider/dashboard
  Blocked from    /admin/* (redirect to provider portal)
  Can             See own appointments, own booking link, limited catalog edits

--------------------------------------------------------------------------------
5E. CUSTOMER (REGISTERED END USER)
--------------------------------------------------------------------------------

  Entry           Must use tenant link: /register?org=demo-company
  API             POST /auth/register with orgSlug in body
  Backend         auth.service register():
                    - Requires orgSlug
                    - Rejects platform org slug
                    - Rejects inactive org
                    - Creates User role customer + Customer profile row
                    - Email verification required before login
  Login           /login  →  /account
  Appointments    GET customer appointments filtered by:
                    organizationId = user.organizationId
                    AND customer.email = user.email

  Guest booking   No account; book on /book?org=…; manage via magic link token

  Files:
    apps/web/src/app/(auth)/register/page.tsx
    apps/api/src/auth/auth.service.ts  (register, getCustomerAppointments)
    apps/web/src/app/account/page.tsx

--------------------------------------------------------------------------------
5F. SUPER ADMIN SUSPENDS A TENANT
--------------------------------------------------------------------------------

  UI              /platform/organizations → Suspend / Activate
  API             PATCH /platform/organizations/:id  { isActive: false }
  Effect          integration + booking validation + appointments.book()
                  reject inactive organizations
  Customers       See forbidden / “not accepting bookings” on API;
                  register blocked with clear message

STEP 3 — Platform API module (NestJS)
  apps/api/src/platform/

    platform.service.ts      — business logic; tenantWhere() excludes platform slug

  apps/web/src/lib/auth-redirect.ts

STEP 7 — Web: platform portal (super admin UI)

7. LOGIN REDIRECTS AND PORTAL SEPARATION
================================================================================

Single login page: apps/web/src/app/(auth)/login/page.tsx

After successful login, resolvePostLoginPath(role, next) chooses:

  super_admin      → /platform/dashboard  (or safe /platform/* next param)
  org_admin        → /admin/dashboard     (or safe /admin/* next)
  location_manager → /admin/dashboard
  provider         → /provider/dashboard
  customer         → /account             (or safe non-admin next)

“Safe next” prevents open redirects and cross-role portal hopping.

Session hooks:

  usePlatformSession   — platform routes only; else login with ?next=
  useStaffSession      — admin/provider staff; rejects super_admin
  (customer account layout uses its own guard)

Visual parity:
  Super admin uses the SAME AdminLayout component as tenant admin, with
  platform nav config and PlatformScopeSwitcher instead of LocationSwitcher.

8. SECURITY RULES (API + UI)
================================================================================

  Rule                                    Where enforced
  ─────────────────────────────────────   ───────────────────────────────────
  Platform APIs need super_admin          PlatformAdminGuard
  Tenant admin APIs need staff + org      JwtAuthGuard, RolesGuard, org in JWT
  Customer register needs valid org slug  auth.service register()
  Public booking needs active tenant org  integration + booking-validation
  Platform org invisible to public        isPlatformOrgSlug() → 404/Not found
  Partner API keys belong to one org      partner-api-key.guard (org on key)
  UI blocks wrong portal for role         layout.tsx + session hooks

Note: Super admin JWT still carries platform organizationId. Tenant-scoped admin
APIs are intended for org_admin users; super admin should use /platform/* APIs.
(Enforcement is primarily by UI redirect + platform guard; avoid sharing super
admin cookie on tenant-only dangerous operations without extra checks.)

9. SUSPENDING A TENANT
================================================================================

  Field: Organization.isActive (default true)

  When false:
    - GET integration booking context → 403 Forbidden
    - New appointments via book() → rejected
    - Customer registration on that slug → BadRequest
    - Existing appointments may still exist in DB; manage links may still work
      depending on product rules (check manage token flow if hard block needed)

  Super admin restores access with PATCH isActive: true from platform UI.

================================================================================
11. KNOWN LIMITATIONS
================================================================================

  - Customer email is globally unique in User table; same person cannot have two
    customer accounts on different tenants with one email (product limitation).

  - Many marketing links still point to bare /book; users see OrgRequiredGate
    until links include ?org=.

  - Super admin can technically call some tenant APIs if they craft requests;
    primary separation is UI + platform module.

  - Platform notifications page is a stub; tenant notifications live under admin.

  - location_manager and provider are staff but not “org admin”; nav items differ.
